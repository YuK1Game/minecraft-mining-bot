## 更新・移行

**Bot本体とダッシュボードの再起動が必要です。** `host.js` を変更しているので、行動コードのホットリロードだけでは全変更は反映されません。GitHub上の変更だけでは、既に動いているPCのBotは更新されません。

1. 既存の未コミット変更を保全し、`/quarry pause` の終了を確認します。`STOPPING` の間は開始・再開できません。
2. `.local/quarry` をバックアップします。認証情報・`.env`・`.auth`・実ジョブのJSONをリポジトリへ追加しないでください。
3. Botと監視サーバーを終了し、変更ブランチまたはマージ済みのソースへ更新します。
4. Node 24で `npm ci`、`npm run check`、`npm run test:review` を実行します。
5. 接続先Realmとプロフィールを確認して接続専用モードで起動します。`/quarry status` と停止理由を確認してから再開します。

旧ジョブは保存済み `scope` から所属ワールドを復元できます。現在の接続先から所属を推測して埋めることはしません。古いJSONにワールド情報がなければ `WORLD_IDENTITY_UNKNOWN` で停止します。異なるワールドのJSONを手で現在のRealm IDへ書き換えて再開してはいけません。

ジョブIDは英数字で開始する1～80文字の英数字・`_`・`-`・`.`です。末尾の`.`、パス区切り、Windowsの予約名などは拒否します。大文字小文字だけが違う同名ファイルも拒否します。既定の新規IDはUUIDです。同じIDを別の新規計画へ再利用した場合は保存時に `JOB_ID_COLLISION` で止まり、古いジョブを上書きしません。

## 保存失敗・停止未確定の対処

`PERSISTENCE_FAILED` は、空き容量、アクセス権、ファイルロックなどを先に解消します。通常の `/quarry resume` で上書きして進むことはできません。停止中に次のローカルAPIで保存だけを明示的に再試行します。

```powershell
$body = @{ group = 'quarry'; method = 'retryPersistence'; args = @() } | ConvertTo-Json
Invoke-RestMethod -Method Post -ContentType 'application/json' -Body $body http://127.0.0.1:3000/action
```

再試行成功後も手動一時停止のままです。`persistence.status`、`pauseReason`、未確定の収納・設置を確認してから `/quarry resume` を使います。失敗時にディスクへ何も書けない状況では、停止意思の永続化も保証できません。エラー表示を無視して再起動・自動再開を繰り返さないでください。

`STOP_UNCONFIRMED` はキャンセル要求を送ったものの、旧操作が終了したと確認できない状態です。期限切れを成功扱いにせず、未終了の操作が残る間は新しいworkerを開始しません。切断・再起動で対処する場合も、保存済みの操作意図と実際のワールド・所持品を照合する必要があります。

Windows等でディレクトリfsyncが利用できない場合は `directorySynced:false` と区別します。ファイルfsyncや原子的renameを実装したことと、あらゆるOS・ストレージ・電源断で損失がないことは同義ではありません。物理的な電源断試験は未実施です。同じ作業ディレクトリへ複数Botプロセスで書き込む運用は非対応です。

## 脱出の予備検査

予備検査は読み取り専用です。掘る予定の入口を「掘った」と見なしたり、地形要求を送っただけで未知セルを既知にしたりしません。`exitPreflight.predictionOnly` と実際の `surfaceReturned` は別です。

安全な列を確認できない場合、これから始める掘削を止めます。資材が不足する場合は確認済みの補給設定で補給を試み、解消できなければ不足理由を表示します。予約した列を通常の止水・施工で塞がず、脱出に必要な道具使用回数も採掘から取り分けます。採掘開始後にプレイヤーや環境が変えた地形まで保証するものではなく、層変更時と最終脱出時に再評価します。

## 検証コマンドと結果の読み方

```sh
npm run check
npm run test:review
npm run benchmark:combat
npm run test:compare -- <基準コミットSHA>
```

`check` は `src/`・`scripts/`・`test/` のJavaScriptとダッシュボード内スクリプトを確認します。`test:review` は今回追加した回帰テストと関係する既存の互換テストを実行します。最後の比較コマンドは基準版の一時worktreeと現在版を同じNode・依存パッケージで実行し、`test-results/` に両方のTAPと `comparison.json` を出力します。

既存全テストには `.local/operator-live-helpers.cjs` など未コミットのローカル資産を必要とするテストや、基準版から失敗するテストがあります。CIはそれらを成功へ書き換えたり、全件をskipしたりしません。新しい失敗の増加を比較で検出します。**比較が成功しても既存全件が成功した意味ではありません。** 途中で切れたTAPは比較成功にできません。基準から失敗しているテストの新たな問題をすべて検出できる保証もないため、新規の独立した回帰テストを併用しています。

合成負荷ベンチマークは100個の敵経路問い合わせを同じ予算窓へ与えます。測定対象は経路探索部分であり、実Realm全体のCPU時間・通信遅延・戦闘勝率ではありません。

## 実Realmの受け入れ確認（未実施）

以下はオフラインテストでは代替できません。サンドボックスの小さい範囲で、既存ジョブ・建築物を保全して確認します。

- 同じRealmで再接続したときだけ復旧でき、別Realm・別次元ではブロック操作が出ない。
- 採掘中、設置中、収納中、柱上昇中の停止と再起動で、未確定の操作を二重送信しない。
- 実際の収納・シュルカー内容・道具耐久・土の減少と地上帰還がすべて受信証拠で一致する。
- 多数の敵・地形更新時の探索時間、入力周期、脅威への反応が許容範囲である。
- Windows実機でログ回転中の監視、低速閲覧、ファイルロック、ディスク容量不足を扱える。

オフラインの一連動作テストは、採掘→回収→収納→脱出用採掘→柱→地上帰還を実際のジョブ/脱出コントローラで接続しています。ただし、移動・採掘・設置のサーバー観測は制御したテスト用アダプタであり、実サーバー・実ジャンプ物理の成功を主張しません。
