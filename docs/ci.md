# CI とテストの実行時間

CI（`.github/workflows/ci.yml`、「Bot regression CI」）が何を実行するか、どこに時間がかかるか、速さを保つための決まりをまとめます。2026-11-18 に、1回の push で約19分かかっていたものを見直しました（ユーザー指示「遅すぎるので不要なテストは減らし、遅すぎるテストは改善して」）。

## 何を実行するか

| ジョブ | 内容 | 失敗の条件 |
| --- | --- | --- |
| safety regressions（ubuntu・windows） | `npm run check`、`npm run test:review`、`npm run test:player`、`npm run benchmark:combat` | テストの失敗が1件でもあれば失敗 |
| Complete suite / compare with base（3分割、ubuntu） | 上の2つのレーンに入っていないテスト全件を、基準のコミットと比べる（`npm run test:compare`） | 基準になかった失敗があれば失敗。前からの失敗は報告に残す |

- push で動くのは `main` だけです。ブランチは PR で確認されます（以前は push と PR で同じ内容が2回動いていました）。
- 2つの厳格なレーン（`test:review`・`test:player`）のファイルは、全件比較では実行しません。同じ push で、より厳しい条件（全部合格）で必ず実行されるためです。どのファイルがどのレーンかは `scripts/lib/test-lanes.js` が決めます。
- 全件比較は、ファイル名から決まる3つの組に分けて、別々のマシンで実行します（`SUITE_SHARD=1/3` など）。元のファイルと `.partN.test.js` は同じ組にまとめ、組の中では別プロセスとして並列に実行します。テストを追加して所属する part が変わっても、そのテストの比較先は変わりません。ほかのファイルの増減でも組は変わりません。

## 基準の結果を使い回す

全件比較は、基準のコミットと変更後の両方でテスト全件を実行していました。基準のコミットは push のたびに変わらないので、その結果を残して使い回します。

- `main` の実行は、そのコミットの結果を `actions/cache` に残します（キーはコミット・組・OS と、下記の入力・設定の fingerprint）。
- PR の実行は、基準のコミットの結果が残っていればそれを読み、変更後の側だけを実行します。残っていない時（`main` の実行がまだ終わっていない時など）は、以前と同じく基準も実行し、その結果をその PR 用に残します。
- 残した結果を使うのは、同じコミット・同じ組・同じ入力と設定の時だけです。`package.json`・lockfile、比較・テスト選択・出力収集のコード、Node の完全なバージョン、OS・CPU アーキテクチャ、`NODE_OPTIONS`、並列数を照合します。基準を実行する時も変更後の `node_modules` を使うため、依存関係が変わったら過去の結果は使わず、基準を取り直します（`scripts/lib/suite-store.js`）。
- `node scripts/compare-tests.js --cache-key` は同じ入力・設定から Actions 用の fingerprint を出力します。この実行ではテストや Git 操作を始めません。restore と2つの save はすべて同じ fingerprint を使うため、古い依存関係や選択ルールのキャッシュを別の実行へ持ち越しません。壊れた結果も使いません。
- 基準のコミットのチェックアウト（一時的な Git ワークツリー）は、基準を実行する時（結果が残っていない時、基準に結果のないファイルを実行し直す時、新しい失敗のファイルを基準で単独で確かめる時）にだけ作ります。
- 手元では `test-results/suite-reports/` に残ります。同じ基準で2回目からは変更後の側だけを実行します。`SUITE_REPORT_DIR=none` で使い回しをやめられます。

## 遅かった原因と直したこと（2026-11-18）

ファイルごとの時間は、各ファイルを単独で実行して測りました（Node 24、4コア、`--test-timeout=30000`。603ファイルの合計は約19分ぶん）。

| 原因 | 計測 | 直したこと |
| --- | --- | --- |
| `test/quarry-job.test.js`（露天掘りのジョブ全体を35回シミュレートする） | 単独で197秒。安全回帰レーンの時間のほとんどがこの1ファイル | 計画の到達範囲の探索（`src/quarry/quarry-planner.js` の `reachableSearch`・`pathTo`）で、同じマスに立てるかどうかを1回の探索の中で何度も調べ直していたのをやめた（答えは同じ）。101秒になり、さらに3つのプロセスに分けて36秒 |
| `test/runtime-idle-escape.test.js`（実 Runtime のテスト196件） | 単独で246秒。メモリの少ない環境では110件目でメモリ不足で終了し、残りは実行されていなかった | 物理予測を作るたびにブロックの状態の表（約1.5万件）を作り直していたのを、レジストリごとに1回にした（`src/movement/physics.js`。1回あたり約50ms、Runtime 1つで3回）。テスト側の地形の複製を軽くした。4つのプロセスに分けて49秒 |
| 来ないものを30秒の上限まで待つテスト3件（`autonomy`・`runtime-distant-food`・`runtime-food-reserve`） | 各30秒 | 前からの失敗で、失敗のしかた（時間切れ）は変えずに、上限を3秒にした |
| 全件を毎回2周 | 全件比較のステップが14〜19分 | 上の「基準の結果を使い回す」 |
| push と PR の2重実行 | 同じ6ジョブが2回 | push は `main` だけ |
| 厳格なレーンと全件比較の2重実行 | 135ファイル（全体の時間の約4分の1） | 全件比較から外した |
| 実時間を見るテストが、マシンの速さで合否が変わる（`test/runtime-close-creeper-choice.test.js`。CI では基準のマシンで合格し、次のマシンで2回失敗。手元では変更前も後も3回に2回失敗） | 1回の同期処理が150〜250ms（入力のタイマーが tick を飛ばす） | 共通の模擬Runtime（`test/runtime-idle-safety.test.js`、14ファイルが使う）が地形を1マス読むたびに `structuredClone` で複製していたのを、ふつうのデータは手で複製する形にした。同期処理は最大92ms になり、6回続けて合格 |
| 強制終了で報告が欠ける（#322 を入れた直後の `main` の実行で、3組目の報告に合計がなく、2回続けて「報告が不完全」で失敗した。テストの失敗ではない） | 同じ組を3回実行して、報告されたテストが 1312・1303・1312 件。小さなテスト481件のスイートでは 436〜457 件（終了コードは 0） | 全件比較は、終わらないタイマーを残す古いテストのために `--test-force-exit` で実行する。強制終了は出力を待たず、Linux のパイプは非同期に書くので、読み手がまだ受け取っていない分（パイプの64KBを超えた分）が捨てられる。テストファイルは結果をパイプでランナーへ送り、ランナーも報告をパイプで書く。`scripts/lib/blocking-output.js` を全プロセスに読み込ませ（`NODE_OPTIONS --require`）、パイプへの書き込みを同期にした。それより前に残した結果は使わない（設定に `output` を足した） |

長いファイルを複数のプロセスに分ける形: ファイルの先頭で `test` を包み、N個のうち自分の番のテストだけを登録します。`<名前>.partN.test.js` は番号を設定して元のファイルを読み込むだけです。テストは元のファイルから登録されるので、結果の名前とファイル名は変わりません。各 part は同じ CI の組で比較します。基準の結果が欠けた時や新しい失敗を再確認する時は、結果に出た元のファイルだけでなく、その側にある全 part を再実行します。

2026-11-18 のレビューでは、成功テストを1件足しただけで既存失敗の所属 part が移り、別の組で新規失敗と判定されることと、古い依存関係での失敗をキャッシュが既存失敗として許容してしまうことを再現しました。`test/review-suite-comparison.test.js` は、小さなテストプロジェクトを実際の runner と比較処理に通し、この2件と全 part の再実行を確認します。

この高速化でテストは削除していません。当時、1件も通らないファイル27個の合計は36秒（全体の約3%）でした。この件数は当時の計測で、現在の残件数ではありません。

## Runtime fixture の修復と残る失敗

修復前の `main`（`083b482`）の[全件比較ログ](https://github.com/YuK1Game/minecraft-mining-bot/actions/runs/44907039273)は、4,336件中3,959成功・373失敗・3中断・1スキップです。新しい失敗がないためCIが成功していることと、全件成功は別です。このうち12ファイル・71件は `Cannot find module '../common/work-spans'` により、本来の検証へ到達していませんでした。

原因はテストが分割済みの Runtime を一つの文字列へ戻す際に、各モジュールの相対パスとファイル先頭の依存を失っていたことです。パスだけを直すと、次は `createDragonRuntimePorts` が未定義になります。`test/helpers/runtime-fixture.js` は実ファイルのスコープと相対 `require` を保持して読み込み、依存の差し替えを解決済みのモジュール名へそろえます。テストごとに Runtime の分割モジュールを隔離するので、反実仮想の変更が次のテストへ残りません。

観測には共通の `inspection`、依存の差し替えには `runtimeOverrides`、限定した反実仮想にはファイル名を指定する `runtimeHooks.transforms` を使います。入力ソースの改行をそろえてから変換し、観測点が一意に一致することを確認します。Windowsの改行をRuntime本体と分割モジュールへ与える回帰も `review-runtime-fixture.test.js` で検査します。実 Runtime と対象の分割モジュールを読み込み、外部サービスの差し替えは既存 fixture の境界に限定します。Runtime 自体を成功固定値へ置き換えません。旧 `runtime-source.js` はソース構造を調べる既存テスト用に残し、今回の実行テストは使いません。

| 確認範囲 | 手元の結果（Node 24） |
| --- | --- |
| 元の12ファイル：戦闘入力・操作権、生存回の受信、食料優先、被弾退避、移動の空腹制御、小屋、岸の順位、水中の敵情報、作業停止と期限、短距離移動 | 82件中81成功・失敗0・中断0・既存スキップ1、約12秒 |
| 共通 `runtime-user-behaviors.test.js` 本体 | 24件すべて成功、約1.2秒 |

旧期待は現仕様の根拠を確認して更新しました。戦闘開始は既存の待機退避より優先し、旧モードは木材不足でも無許可で伐採しません。プレイヤーモードでの自然木の採取と、旧モードで所持原木を使う準備も別に確認しています。水中退避で個体ID・危険半径が変わった場合は、保持個体の再照合で中断し、移動開始・入力フレームがともに0であることを確認します。テストの削除・新たなスキップ・比較基準の緩和はしていません。

上は対象を絞った手元の結果です。他の既存失敗や、全件比較の最新件数は各CIのレポートで確認します。共通 fixture の互換確認で見えた `runtime-autonomy-resume.test.js` の2件は、修復前のCIにも同じ名前・種類で存在し、今回の対象には含めていません。

## ローカル専用 helper への依存を禁止する

2026-11-26 の修正で、`low-health-recovery`、`operator-timed-work-helper`、`operator-transient-transport`、`archer-work-floor`、`runtime-eventloop-fairness` を厳格な安全回帰レーンへ追加した。前のコードでは無視対象の `.local/` の helper がなく、検証本体を読み込めないまま全件比較の既存失敗として残っていた。

手動操作 client は `scripts/lib/operator-helpers.js` に置き、テストから同じ実装を呼ぶ。移動は受信した期限付き作業leaseを使い、プレビュー後にも危険と接続・生存回を読み直す。終了時は実際の開始印・目的地が一致する移動だけを止め、自分のlease IDだけを解放する。保護controllerの停止や、予測をサーバー到着へ変える処理は行わない。モジュールを読み込むだけでは通信しない。

イベントループのテストは `test/helpers/runtime-fixture.js` から実 Runtime のモジュール構成をそのまま実行する。過去のソース変更パッチは不要になった。`.local/staged/` にある別コピーへのフォールバックも廃止し、管理されている実装・fixtureだけを既定で読む。`review-test-dependencies` が全テストを監査し、ローカル専用helper/fixtureへの参照が再び入れば厳格レーンを失敗させる。単独確認は `node scripts/audit-tests.js --strict`。

## 速さを保つための決まり

1. 1つのテストファイルが単独で30秒を超えたら、原因を直すか、上の形で複数のプロセスに分ける。
2. 来ないものを上限まで待つテストを足さない。待つ時は、待つ理由のある短い上限を付ける。
   実時間を見るテスト（入力の tick が連続している、など）は、模擬の側の重い処理（地形の複製など）で合否が変わらないようにする。全件比較は基準の結果を別の実行から読むので、マシンの速さで合否が変わるテストは「新しい失敗」に見える。そのため比較は両側を同じやり方で確かめる: 新しい失敗は、そのファイルを変更後のコードでもう一度実行し、まだ失敗するものだけを、基準のコミットでもそのファイルだけを実行して確かめる。基準でも同じ失敗（同じファイル・名前・種類・コード）になるものは新しい失敗に数えず、結果の `failsOnBaseAlone` に出す（2026-11-18 PR #329: `test/runtime-learning-shore-executor.test.js` の「uid change …」は main でも単独では毎回失敗するが、4並列の全件実行では操作が時間切れになって合格と記録され、変更後の失敗が新しい失敗と数えられた）。
3. 厳格なレーンに入れたファイルは全件比較では実行されない。レーンの増減は `scripts/lib/test-lanes.js` で行う。
4. 分割数を変える時は、`ci.yml` の `part` の一覧、`SUITE_SHARD`、3つのキャッシュのキーをそろえる（`test/review-suite-store.test.js` が確かめる）。
5. テストを `--test-force-exit` で実行する時は、出力をパイプのまま強制終了させない（`scripts/lib/blocking-output.js`）。件数が実行ごとに変わる報告は、失敗を黙って落とす。
